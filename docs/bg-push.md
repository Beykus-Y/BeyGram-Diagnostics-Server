# BG Push: уведомления на iPhone через PWA

BG Push — опциональный модуль сервера. Он нужен, потому что нативный форк BeyGram для iOS
без платной Apple Developer Program не может использовать APNs приложения. Установленная на
экран «Домой» PWA на iOS 16.4 и новее получает Web Push без платной программы разработчика.

Модуль выключен по умолчанию (`ENABLE_PUSH=false`). Android и Desktop работают напрямую через
Telegram и через BG Push не проходят.

> **Статус: серверная часть и PWA-компаньон написаны и покрыты автоматическими тестами.
> На реальном iPhone и с реальным форматом Telegram не проверено.** Раздел «Что не проверено»
> нужно прочитать до включения модуля в продакшене.

## Поток доставки

```text
Telegram (account.registerDevice, token_type=10, endpoint = ingress_url)
  -> POST /api/v1/push/ingress/<capability>   внутренний слой зашифрован ключом устройства
  -> очередь push_deliveries (отдельная SQLite-база)
  -> воркер: внешний слой RFC 8291 + VAPID     -> push-сервис браузера (Apple, Mozilla, FCM)
  -> service worker PWA расшифровывает внутренний слой на устройстве
  -> системное уведомление -> клик -> /push/open#beygram://push/open?... -> BeyGram
```

Сервер не расшифровывает содержимое Telegram и не имеет приватного ключа ингресса.
Ключи ингресса создаёт PWA на устройстве; серверу передаются только публичный ключ и auth-секрет.

## Что не проверено

Эти пункты нельзя подтвердить автоматическими тестами. Они входят в прототип из issue #30 (пункт 0).

- **Реальный iPhone.** Установка PWA, выдача разрешения по жесту, доставка при закрытых приложениях,
  при блокировке и после перезагрузки, переход в BeyGram. Симулятор не доказывает фоновую доставку.
- **Формат Telegram.** Неизвестно, как Telegram шифрует payload на ингресс и какие у него поля.
  PWA разбирает только собственный тестовый формат v1. До прототипа реальные уведомления
  показываются как общее «Новое уведомление» без перехода в чат.
- **Параметры registerDevice.** Значения `secret` и `app_sandbox` для token_type 10 не проверены.
  Сервер эти поля не использует.
- **Решение go/no-go.** Принимает владелец проекта по результатам прототипа на реальном аккаунте.

## Включение

1. Создать ключи. Команда создаёт файлы с правами 0600 и не перезаписывает существующие:

   ```bash
   python -m app.push.keygen /data/push
   ```

   Команда печатает публичный `applicationServerKey` и пути к файлам, содержимое ключей не выводит.

2. Заполнить `.env` (блок BG Push есть в `.env.example`):

   ```ini
   ENABLE_PUSH=true
   PUSH_PUBLIC_BASE_URL=https://<домен сервера>
   PUSH_VAPID_PRIVATE_KEY_FILE=/data/push/vapid_private.pem
   PUSH_VAPID_SUBJECT=mailto:<адрес>
   PUSH_STORAGE_KEY_FILE=/data/push/storage.key
   PUSH_DATABASE_PATH=/data/push/bg_push.db
   ```

   Если `ENABLE_PUSH=true`, сервер не стартует без ключевых файлов и адреса с HTTPS.

3. Перезапустить сервис. `/readyz` покажет поле `push`. Его статус отдельный и не меняет общий статус сервера.

## Ключи и резервные копии

- `vapid_private.pem` — закрытый ключ VAPID. Его смена требует повторной подписки всех PWA-устройств.
- `storage.key` — ключ шифрования полей push-базы. Без него зашифрованные адреса и ключи устройств
  нечитаемы, и привязки придётся создать заново.
- Ключи не хранить в git и не класть в базу. Резервные копии базы и ключей хранить раздельно.

## Nginx

Пути, которые нужно пропустить к приложению:

- `/push/` (страницы PWA, `sw.js`, манифест, ассеты) и `/api/v1/push/`;
- `/admin/push` — только за той же защитой, что и остальная админка.

Capability находится в пути URL и является секретом. Приложение скрывает его в своих логах, но журнал
прокси пишет полный путь, поэтому для ингресса журнал прокси нужно отключить:

```nginx
location ~ ^/api/v1/push/ingress/ {
    access_log off;                 # в пути capability; журнал прокси не должен его писать
    client_max_body_size 4k;        # PUSH_MAX_INGRESS_BYTES = 3900
    proxy_pass http://app;          # ваш upstream
}
```

Блок должен стоять до общего `location /api/`, потому что regex-локации проверяются раньше префиксных.
IP клиента сервер определяет так же, как для остального API (см. настройки доверенного прокси).

Остальные push-пути не содержат секретов в URL: код привязки передаётся во фрагменте (`#`), который браузер
не отправляет на сервер.

## Kill switches

В админке `/admin/push` есть два независимых переключателя:

- приём ингресса: при выключении новые уведомления получают 503;
- отправка: при выключении очередь копится до TTL и затем истекает.

Отзыв регистрации и удаление работают при любом положении переключателей.

## Хранение и удаление

- `push_deliveries` хранит уже зашифрованное тело записи до доставки или истечения TTL
  (`PUSH_DEFAULT_TTL_SECONDS` по умолчанию 3600, максимум `PUSH_MAX_TTL_SECONDS` 86400).
  Устаревшие записи удаляются при обслуживании.
- `push_registrations` хранит адрес PWA-подписки и ключи в зашифрованном виде (AES-256-GCM, ключ вне базы,
  контекст привязан к записи). Идентификаторы и секреты хранятся только как HMAC-дайджесты.
- При отзыве зашифрованные поля подписки и ключи обнуляются.
- `push_counters` — суточные агрегаты без идентификаторов, для админки.
- Удаление регистрации владельцем или устройством не требует работающей отправки.

## Приватность

Сервер не хранит и не логирует: содержимое уведомлений, закрытый ключ ингресса, capability, код привязки,
bearer-токены, адреса push-сервисов, ключи p256dh и auth в открытом виде. Админка показывает агрегаты и статусы
без содержимого.

Границы доверия: веб-origin и обновления PWA считаются доверенными. Сервер видит время и объём уведомлений
и адрес подписки, но не их текст. Полностью враждебный origin или атака на цепочку поставки не покрываются.

## API для нативного клиента

База: `/api/v1/push`. Владелец генерирует 256-битный секрет (base64url, 43 символа) и передаёт его в
`Authorization: Bearer`. Сервер хранит только его дайджест и не выдаёт свой.

| Метод и путь | Назначение | Ответ |
|---|---|---|
| `GET /config` | публичные параметры для PWA | `enabled`, `vapid_public_key` |
| `POST /registrations` | создать привязку (владелец) | 201: `registration_id`, `state`, `expires_at`, `ingress_url`, `pairing_code`, `setup_url` |
| `GET /registrations/{id}` | статус (владелец или устройство) | `state`, `telegram_confirmed_at`, `last_push_ok_at`, `ack_at`; владельцу при `active` ещё `telegram_keys` |
| `POST /registrations/{id}/complete` | завершить привязку (PWA, секрет из кода) | 200: `registration_id`, `state`, `token` |
| `POST /registrations/{id}/telegram-confirm` | подтвердить регистрацию в Telegram (владелец) | `ok`, `telegram_confirmed_at` |
| `POST /registrations/{id}/test` | тестовое уведомление (владелец или устройство) | 202: `test_id`; 409, если привязка не активна |
| `POST /registrations/{id}/ack` | подтверждение получения (PWA) | `acknowledged` |
| `DELETE /registrations/{id}` | отзыв (владелец или устройство; повтор безопасен) | `deleted` |
| `POST /ingress/{capability}` | приём Telegram Web Push (без Bearer) | 201 |

Регистрация в Telegram: `account.registerDevice(token_type=10, token=JSON)`, где JSON содержит
`endpoint` = `ingress_url` и `keys` = `telegram_keys`. Ключи подписки браузера в этот JSON не входят.
Порядок: создать привязку, дождаться `state=active`, зарегистрировать в Telegram, вызвать `telegram-confirm`.
При отзыве: `DELETE`, затем `account.unregisterDevice` с тем же токеном.

Ошибки приходят в формате `{"error": {"code", "message"}}`.

Переход из уведомления: `beygram://push/open?account=<id>&peer=<id>&msg=<id>`. Все параметры необязательны.
Без них нативный клиент открывает список чатов. PWA строит ссылку только из числовых полей и не исполняет
URL из payload. Проверку `account`, `peer` и `msg` выполняет нативный клиент.

## Открытые решения

Эти вопросы решает владелец проекта. Автоматически их не закрыть.

- **Подтверждение привязки.** Кто первым предъявит код привязки, тот подставит свой endpoint и ключи ингресса.
  Код живёт 10 минут и виден в адресной строке и буфере обмена, поэтому перехват возможен. Вариант защиты:
  нативный клиент показывает владельцу хост endpoint и отпечаток ключа и регистрирует ключи в Telegram
  только после подтверждения. Требует изменения клиента.
- **Ключ хранения рядом с базой.** По умолчанию `storage.key` лежит в том же каталоге, что `bg_push.db`,
  и резервная копия каталога заберёт оба файла. Рекомендуется отдельный том или каталог для ключей.
- **Суффиксы в `PUSH_ALLOWED_ENDPOINT_HOSTS`.** Совпадение по суффиксу пропускает любой поддомен.
  Не добавляйте общие домены облачных хостингов, только конкретные push-провайдеры.
- **Общий origin.** PWA, токен в IndexedDB и API работают на том же origin, что и админка. XSS в любой из этих
  частей даст доступ к токену устройства. Вариант: отдельный origin для `/push/`.
- **`/readyz`.** Поле `push` открыто, как и остальные поля readyz. Если readyz публичен, урежьте его до статуса.

## Тесты

```bash
python -m pytest tests -q
BG_PYTHON=/путь/к/python node --test tests/js/bg-core.test.mjs
```

Второй набор проверяет расшифровку PWA на записи, созданной серверной функцией шифрования. Нужны Node 22 и
python с пакетом `cryptography` (например, из venv сервера).

## Диагностика

- `503 push_disabled` — модуль выключен (`ENABLE_PUSH=false`) или не инициализирован.
- `409 registration_inactive` — тест для привязки, которая не активна.
- `429 rate_limited` — превышен лимит. Окна описаны в переменных `RL_PUSH_*` в `.env.example`.
- Провайдер ответил 404 или 410 — регистрация отзывается автоматически. Нужна новая привязка в PWA.
